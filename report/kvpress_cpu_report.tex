\begin{abstract}
This report evaluates four reproduced KV cache compression methods in the
\texttt{kvpress} framework: \texttt{KnormPress}, \texttt{SnapKVPress},
\texttt{AdaKVPress}, and \texttt{StreamingLLMPress}. The benchmark uses
\texttt{EleutherAI/pythia-70m} on WikiText-2 and PG-19 with 1024-token contexts
and 256-token perplexity targets. Throughput is measured only during the decode
stage after prefilling and KV compression, so the reported speed isolates the
effect of a smaller runtime KV cache rather than the one-time compression cost.
On CPU, the strongest quality--speed tradeoff is obtained by \texttt{SnapKVPress}
and \texttt{StreamingLLMPress}: they preserve perplexity well at moderate
compression and improve decode throughput over the uncompressed baseline.
\end{abstract}

\section{Implementation}

The evaluation is implemented in \texttt{pythia\_kvpress\_test.py}. The script
loads \texttt{EleutherAI/pythia-70m} with Hugging Face Transformers and evaluates
the same model across all presses. When \texttt{--device cpu} is used, the model
runs in \texttt{float32} and results are written to
\texttt{results/cpu\_base\_test}. The reproduced run analyzed here is:
\begin{center}
\small
\texttt{python pythia\_kvpress\_test.py --output-csv ctxt1024\_tar\_256\_try\_cpu.csv --device cpu}
\end{center}

\paragraph{Compared methods.}
The dense baseline is implemented as \texttt{NoPress}, which leaves the KV cache
unchanged. The four compression methods are constructed through
\texttt{build\_press}. \texttt{KnormPress} is a score-based method that ranks KV
entries by the negative key-vector norm in the current implementation.
\texttt{SnapKVPress} scores old tokens by the average attention received from a
recent observation window, with a default window size of 64 tokens, and protects
the observation window from pruning. \texttt{AdaKVPress} wraps
\texttt{SnapKVPress} and applies adaptive head-wise compression: it uses the base
scores but prunes across heads with a safeguard so that each KV head keeps a
minimum fraction of its budget. \texttt{StreamingLLMPress} implements the
attention-sink and recent-window strategy: it keeps the first sink tokens and
the most recent tokens, while pruning tokens in the middle.

\paragraph{Perplexity evaluation.}
For each dataset, the script builds non-overlapping token windows. Each window
contains 1024 context tokens and 256 target tokens. The context is first passed
through the model inside the press hook, so the returned \texttt{past\_key\_values}
are already compressed for every method except \texttt{NoPress}. The first
target token is scored from the final context logit, and the remaining target
tokens are scored using teacher forcing with the compressed cache. The code
keeps absolute \texttt{position\_ids} on the original context timeline, while
\texttt{cache\_position} follows the physical compressed-cache length when the
model exposes that argument. This distinction is important because KV
compression shortens the stored cache but should not change the semantic token
positions used by RoPE.

\paragraph{Throughput evaluation.}
The script measures decode throughput after the prefill and compression stages.
For \texttt{NoPress}, timing starts after the uncompressed prefill. For compressed
methods, timing starts after the context has been prefilling-compressed and
after a fixed question prompt has been added to the cache. The timed loop then
generates 64 greedy tokens, and throughput is computed as generated tokens
divided by the timed decode latency. This measurement answers a specific
question: how much faster is token-by-token decoding once the cache has already
been reduced? It intentionally excludes the one-time scoring and compression
cost.

\section{Analysis}

\paragraph{Why throughput improves.}
During autoregressive decoding, each new token attends to all cached keys and
values. After prefill-time compression, the cache length is reduced from the
original 1024 context tokens to roughly \(1024(1-r)\), where \(r\) is the
compression ratio. A shorter cache reduces attention work and memory traffic in
the decode loop. Because the benchmark starts the timer only after prefill and
compression, the measured throughput mostly reflects this smaller cache. This
explains why most methods become faster as the compression ratio increases.

\paragraph{Why PPL degrades with compression.}
Compression removes context information. If removed tokens are needed to predict
the 256 target tokens, perplexity rises. This effect is visible for every
method, especially at ratio 0.8. The quality drop is method-dependent because
each press chooses a different retention policy. \texttt{SnapKVPress} uses
recent attention as a task-adaptive importance signal, so it keeps many tokens
that the current suffix already attends to. \texttt{StreamingLLMPress} is simpler
but strong for long-context decoding because it preserves attention sinks and
the most recent context, which are often disproportionately useful for stable
generation. \texttt{KnormPress} is cheap but less context-aware, and therefore
loses more quality when aggressive pruning removes semantically important
tokens. \texttt{AdaKVPress} does not dominate \texttt{SnapKVPress} in this run:
the head-wise adaptive masking can protect heads unevenly, but with Pythia-70m,
small sample counts, and CPU execution, this extra flexibility does not translate
into a better PPL--throughput tradeoff.

\paragraph{Dataset differences.}
The WikiText-2 results show larger quality degradation than PG-19 for the same
compression ratios. Part of this can be explained by sampling: WikiText-2 uses
three windows, while PG-19 uses a single local sample. The PG-19 result is
therefore more sensitive to the particular passage. Another factor is that
recent-window and sink-token methods are naturally aligned with long-context
continuation: preserving the most recent segment and first few tokens can be
enough for many local predictions, especially when the target follows directly
after the context.

\paragraph{Best operating points.}
For WikiText-2, \texttt{SnapKVPress} at ratio 0.2 is the clearest conservative
choice: PPL rises only from 32.30 to 33.65 while throughput increases from
65.89 to 92.67 tokens/s. If speed is more important, \texttt{StreamingLLMPress}
at ratio 0.6 reaches 99.29 tokens/s but increases PPL to 43.10. For PG-19,
\texttt{StreamingLLMPress} at ratio 0.2 gives the best low-risk result, while
\texttt{SnapKVPress} at ratios 0.4--0.6 gives a strong balance near
98--100 tokens/s with PPL around 23.9.

\section{Conclusion}

The reproduced CPU benchmark confirms the expected tradeoff of KV cache
compression: reducing the cache improves decode throughput after compression,
but aggressive pruning can degrade perplexity. Among the four reproduced
methods, \texttt{SnapKVPress} is the most consistent quality-preserving
compressor, and \texttt{StreamingLLMPress} is a strong simple baseline with high
decode throughput. \texttt{KnormPress} is computationally cheap but less robust
at high compression, while \texttt{AdaKVPress} does not improve over its
SnapKV-based scorer in this Pythia-70m CPU setting. Future evaluation should run
more PG-19 samples and repeat the same sweep on CUDA, where memory bandwidth and
kernel overhead may change the relative throughput ordering.
